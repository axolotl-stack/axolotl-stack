# BDS quirks we copy on purpose

unastar copies BDS 1.26.51 exactly, including behaviour that looks permissive, odd or
buggy (decision D3 in `thoughts/shared/plans/2026-10-24-data-driven-decisions.md`).
Every such behaviour is listed here so it can be revisited one at a time.

| Area | Behaviour BDS shows | How it was observed | Why it looks odd | unastar status |
|---|---|---|---|---|
| World / time | Time is synced only with `SyncWorldClocksPacket`; `SetTime` is never sent | 0 `SetTime` vs 54 `SyncWorldClocks` across 14 captured BDS 1.26.51 sessions (`tools/client-diff/conformance-report.md:121`) | Older servers and most third-party servers drive the client clock with `SetTime`; 26.x moved time to a world-clock registry | Planned (world W10); the re-sync cadence still needs a capture with the daylight cycle running |
| World / spawn | `level.dat` stores `SpawnY=32767` and the real spawn Y is resolved later | Seed-12345 reference world behind `crates/unastar/tests/fixtures/bds_1_26_51_seed_12345.json` (`SpawnX=103, SpawnZ=-28, SpawnY=32767`) | A sentinel height is persisted instead of a real block position | Planned (world W3) |
| World / generation | Forced ticking areas do not persist every requested chunk; on a first pass about half of the requested areas were missing on disk after `stop` | Generating the seed-12345 reference world (`examples/bds_worldgen_reference.rs` reports missing chunks) | `tickingarea add … true` suggests the area is generated and saved | Tooling only: the fixture dumper skips missing chunks; not copied into unastar |
| World / features | Feature JSON names blocks by pre-flattening identifiers and legacy states (`minecraft:log` + `old_log_type`, `minecraft:leaves` + `old_leaf_type`, `minecraft:grass`) | `definitions/features` and `features.brarchive` in the BDS 1.26.51 install | The network and world format use flattened names; the server upgrades legacy names when loading features | Planned (world W6): needs a block alias/upgrade table |
| World / features | The newest copy of `minecraft:overworld_underground_coal_ore_feature` has `iterations: 0`, so that rule places nothing | Versioned `vanilla_*` feature packs in the BDS 1.26.51 install | A shipped vanilla rule that is effectively disabled by override rather than removed | Planned (world W6): resolve the version stack and keep the zero-iteration row |
| World / ticking | Expected: random-tick count per chunk scales with the highest non-empty sub-chunk (`randomTickSpeed × floor(2.5 × (top + 1))`), positions come from one global LCG shared by all chunks, and the default `randomtickspeed` is 1 | Expected vanilla behaviour, to be confirmed by a BDS sweep before W11 ships | Java ticks 3 positions per section with a default of 3; a server-wide LCG makes tick positions depend on chunk processing order | Unconfirmed; planned (world W11) |
| Containers | The reply to a client `ContainerClose` carries container type `NONE` (-9, byte `0xf7`), not the type of the window being closed, and `server_initiated_close = false`. | BDS 1.26.51 capture, 2026-10-24: gophertunnel-fork client opens its inventory (`Interact` OpenInventory) and sends `ContainerClose{window 0, type 0xff}`; fixture `crates/valentine/tests/fixtures/conformance/wire_probe.jsonl` (`container_close_reply`). | The window being closed is the inventory (-1); BDS answers with a type that never opens anything. | Copied: `unastar` `handle_container_close` replies with `NONE` (test `inventory_open_and_close_use_bds_container_types`). |
| Containers | The player's own inventory opens as window id 2 on a fresh connection, and BDS answers a `ContainerClose` for window 0 with its own window id 2. | Same capture (`container_open_inventory`, `container_close_request`, `container_close_reply`). | The client's close names window 0; BDS ignores that and echoes the id it allocated. | Not copied yet: unastar opens the inventory as window 0, so request and reply agree. Revisit with the window-id counter (inventory engine slice). |
| Inventory | `CraftRecipeAuto` is only accepted while the inventory screen is open (status 7 `InvalidCraftRequest` when closed), when the request's ingredient descriptors match the recipe's (an `item_tag` descriptor for an item-name recipe gives status 25), and when ingredients are consumed from `CombinedHotbarAndInventory` (12); consuming the same slot through `HotBar` (28) gives status 27 and through `Inventory` (29) status 65. | BDS 1.26.51 probe, 2026-10-24: oak_planks recipe (net id 715), `/give @s oak_log 8`, creative; the accepted request/response are fixtures `craft_recipe_auto_request` / `_response`. | The hotbar slot holds the same stack under either container name; only the combined alias is accepted. | Not implemented (unastar answers every non-creative request with an error). |
| Network | `ItemRegistryPacket` lists items in an internal hash order (starts with `red_concrete_slab`, `bow`, `brain_coral_fan`), not by id or name. | BDS 1.26.51 capture `crates/unastar/src/registry/testdata/bds-1.26.51-item-registry.bin`. | Unordered; the client does not depend on it. | Not copied: unastar sends registry order; the entries themselves match byte for byte. |
| Entities / data | Silverfish `become_angry` has `"remove": {"minecraft:silverfish_calm": {}}` with no `component_groups` key. Expected: BDS loads the file and the remove does nothing | bedrock-samples 1.26.50.4 `silverfish.json:161-163`; the BDS behaviour is to be confirmed with a capture | A vanilla event that looks broken is shipped | Unconfirmed; planned (entities E4): parse and ignore |
| Entities / data | 27 shipped entity files use a compact JSON form: filter groups spelled `AND`/`OR`, `subject` and `operator` as integers (0 = self / equals, 1 = other / not equals), default-valued fields left out, `deals_damage: "no"` for `false` | `behavior_packs/vanilla*` entity files in the BDS 1.26.51 install; the same 27 files in bedrock-samples 1.26.50.4 (1.21.130 had only the readable spelling) | The same pack format has two spellings | Planned (entities E3): the normaliser accepts both |
| Survival: exhaustion | At most one 4-point exhaustion step per tick; surplus waits for the next tick | Not yet captured (fixture F5/F1 in `2026-10-24-data-driven-survival.md`) | Large one-off costs (heal 6) take two ticks to drain | WIP on the parked survival branch: `entity::systems::hunger::tick_exhaustion` |
| Survival: peaceful food | Peaceful drains saturation from exhaustion but never food, and refills food +1 every 10 ticks | Not yet captured | Saturation still empties on peaceful | WIP on the parked survival branch: `tick_exhaustion`/`tick_food` |
| Survival: regeneration timer | The 80-tick regeneration/starvation timer resets on every tick it is not running | Not yet captured | Dipping below 18 food for one tick loses all progress | WIP on the parked survival branch: `tick_food` |
| Survival: starvation floor | Starvation stops at 10 health on easy, at 1 on normal, kills on hard | Minecraft Wiki "Hunger" | Easy leaves the player at half health | WIP on the parked survival branch: `tick_food` |
| Survival: hurt cooldown | A stronger hit inside the 10-tick cooldown deals only the difference, without hurt animation or knockback | Not yet captured (F2) | The second hit is silent | WIP on the parked survival branch: `apply_damage_requests` |
| Survival: creative | Creative players still take void damage and die to `/kill` | Not yet captured (F2) | Creative is otherwise invulnerable | WIP on the parked survival branch: `DamageSource::bypasses_invulnerability` |
| Commands | `AvailableCommands` is byte-identical for a member and an operator join; opping a player who is online sends `UpdateAbilities` (and a chat line) but no new `AvailableCommands` | T1 capture 2026-10-25: two first joins into fresh worlds (member, operator), `commands/member.bin` = `commands/operator.bin`; console `op` during a session (`crates/bds-extractor/README.md`) | The client is sent commands it may not run and filters them by the `UpdateAbilities` command permission itself | Not copied yet: survival S2 replays the captured packet (one packet for every permission level) |
| Entities | `/summon minecraft:villager` and `/summon minecraft:zombie_villager` spawn actors whose `AddActor` type is `minecraft:villager_v2` / `minecraft:zombie_villager_v2` | T1 capture 2026-10-25, `captures/1.26.51/operator/manifest.json` (`actor_type` per summon) | The summoned identifier and the network actor type differ | Not copied yet: entities E6/E7 |
| Inventory / commands | `/replaceitem entity <player> slot.armor.head 0 <item>` and `slot.weapon.offhand` place any item (stick, shield, chestplate, totem); chest, legs and feet only take matching armour; the console reports success even when the slot stays empty | Armour-slot sweep 2026-10-25 (`crates/unastar-data/data/measured/armor_slots.json`, slice of 10 items) | The head slot is not restricted to helmets on the command path | Not copied yet: items I5 |
| Blocks / drops | `/loot spawn … mine …` with a multi-count result (fortune on ores) spawns one item actor per item, each with count 1, not one stack; whether a real block break does the same is still to be checked | Drop sweep 2026-10-25 (`measured/block_drops/diamond_ore.json`, `observed`) | More item actors than needed | Not copied yet: entities E9 / items I12 |
| Blocks / mining | With server-authoritative breaking BDS breaks the block itself once its own progress completes; the client only sends StartDestroyBlock and ContinueDestroyBlock, no PredictDestroyBlock is needed | Mining sweep 2026-10-25 (`tools/bds-sweep` mining job: break event ~149 ticks after the start for stone by hand, consistent over three trials) | The client prediction is not what ends the break | Not copied yet: entities E9 |
