# Unastar Plugin Architecture

Unastar loads WebAssembly components with Wasmtime. Plugins implement the
[`unastar:plugin@0.2.0` WIT world](crates/unastar-api/wit/world.wit); Rust compiler
layout and native dynamic-library ABIs do not cross the host boundary.

## API and Registration

- `crates/unastar-api/wit` defines imported host interfaces, the player resource,
  shared records, and typed event exports.
- `unastar_api::Guest` is generated by `wit-bindgen` and requires every export.
- `unastar_api::Plugin` supplies default event implementations. Boolean callbacks
  return `true` to allow default behavior and `false` to cancel it.
- `#[unastar_api_macros::plugin]` registers a concrete `Plugin` implementation by
  invoking `unastar_api::export_plugin!`, which emits the complete `Guest` bridge.
  Use the attribute or the export macro, not both.

```rust
use unastar_api::{Player, Plugin};
use unastar_api_macros::plugin;

struct MyPlugin;

#[plugin]
impl Plugin for MyPlugin {
    fn on_player_chat(_player: &Player, message: String) -> bool {
        !message.contains("blocked")
    }
}
```

The obsolete native-plugin and event-handler attribute macros have been removed.
Event methods are ordinary typed `Plugin` methods; no serialized event dispatcher
or `GameContext` adapter is involved. The
[example plugin](crates/example-plugin) is the buildable consumer reference.

## Build and Installation

```text
rustup target add --toolchain nightly-2026-03-05 wasm32-wasip2
cargo build -p example_plugin --target wasm32-wasip2
```

Install each plugin in its own directory beneath the server working directory's
`plugins/`, with `plugin.toml` and `plugin.wasm`. For the example, use
`crates/example-plugin/plugin.toml` and
`target/wasm32-wasip2/debug/example_plugin.wasm`. Its manifest subscriptions select
which exported callbacks receive server events. The current WIT package version
is `0.2.0`; the manifest's `api_version` should match it.

## Loading and Host Access

Startup discovery reads manifests and compiles components. The first game tick
instantiates pending components and invokes `on-load`, with the live ECS World
attached for both operations: component start functions can invoke hosts too.
A failed instantiation or `on-load` rejects that plugin.

`HostContext` scopes its raw World attachment to the synchronous Wasmtime call.
The attachment is cleared on return and unwind; callbacks cannot retain a World
reference. Host queries read current ECS state. Player mutation requests become
`PluginAction` entries in the ECS action queue, processed by the server's plugin
action system rather than exposing mutable ECS references to guests.

Player handles and their host entity mappings are scoped to a host invocation;
plugins should obtain and use handles during the current callback, not retain
them for subsequent callbacks.

## Resource Limits

Manifest `[limits]` supports:

| Key | Default | Enforcement |
| --- | --- | --- |
| `max_memory` | `67108864` bytes | `StoreLimits` caps each linear memory at creation and growth; exceeding it traps. |
| `fuel_per_tick` | `10000000` | One instruction budget shared by the plugin's subscribed event callbacks in a tick. |

Instantiation and `on-load` share a separate initialization fuel budget of the
same size. Event callbacks do not replenish one another's budget; the next tick
replenishes it. Epoch interruption remains an independent wall-clock guard,
with the deadline reset for each invocation. Traps are logged; cancellable
callbacks that trap fail closed.

Filesystem capability requests preopen only the plugin directory. Do not infer
that every declared manifest capability has an implemented host interface.

## Cancellable Gameplay

```mermaid
flowchart TD
    Input[Client action] --> Validate[Validate against server state]
    Validate -->|invalid| Correct[Send authoritative correction]
    Validate -->|valid| Queue[Queue event intent]
    Queue --> Dispatch[Dispatch subscribed plugin callbacks]
    Dispatch -->|cancel or trap| Correct
    Dispatch -->|allow| Check[Revalidate current server state]
    Check -->|changed or invalid| Correct
    Check -->|valid| Commit[Apply default behavior once]
```

Block breaks and placements mutate chunks only through the post-dispatch commit
hook. Survival placement consumes one selected server-owned item at commit;
cancellation consumes nothing. Cancelling the clicked-face interaction also
cancels its immediately paired placement intent. Multiple intents targeting the
same block are revalidated, so later intents cannot overwrite an occupied target
or replay a completed break.

Chat packet handling queues `PlayerChat` without broadcasting. The plugin
manager is the sole owner of the default chat broadcast, after all subscribed
callbacks have allowed it; cancellation suppresses that broadcast.

## Verification

```text
cargo test -p unastar -p unastar_api -p unastar_api_macros
cargo clippy -p unastar -p unastar_api -p unastar_api_macros --all-targets -- -D warnings
cargo build -p example_plugin --target wasm32-wasip2
```

Host regressions use real inline Wasm components and canonical resource handles,
so loading, cancellation, memory growth, and fuel exhaustion do not require an
installed cross-compilation target. The macro crate also compiles a consumer
that registers a typed plugin without serialization dependencies.
